# ჭორაობა

„ჭორაობა“ არის HTML/CSS/JavaScript სოციალური ვებაპლიკაცია. ანგარიშები, პოსტები, კომენტარები და ფოტოები Supabase Auth, Postgres და Storage სერვისებში ინახება. ახალი მონაცემების ავტომატურად საჩვენებლად გამოიყენება Supabase Realtime.

აპი **ჯერ არ არის live**: საჭიროა საკუთარი Supabase პროექტის შექმნა, SQL migration-ის გაშვება და პროექტის URL/public key-ის მითითება `supabase-config.js`-ში.

## ფუნქციები

- ელფოსტით რეგისტრაცია, შესვლა და ანგარიშიდან გამოსვლა.
- საერთო ფოტო-ლენტა, მოწონებები, შენახული პოსტები, ძიება და ანონიმური კომენტარები.
- ახალი პოსტებისა და კომენტარების ავტომატური გამოჩენა სხვა მომხმარებლებთან.
- JPG/PNG/WebP ფოტოს ატვირთვა; მაქსიმუმ 5 MB. ბრაუზერი ამოწმებს გამოსახულების წაკითხვადობასა და ზომებს, Storage კი MIME ტიპსა და ფაილის ზომას ზღუდავს.
- პოსტისა და კომენტარის გასაჩივრება.
- დაცული ადმინისტრატორის პანელი: პოსტებისა და კომენტარების მართვა, მომხმარებლის დაბლოკვა და გასაჩივრების განხილვა.
- ერთი სატესტო ფოტო, რომელიც migration-ის დროს ბაზაში ემატება.

## Supabase-ის დაყენება

1. შექმენი ახალი Supabase პროექტი.
2. ახალ პროექტზე გახსენი **SQL Editor → New query**, ჩასვი `supabase.sql`-ის სრული შიგთავსი და გაუშვი ერთხელ ცარიელ პროექტზე. უკვე მოწყობილ ძველ პროექტში გაუშვი მხოლოდ `supabase-delete-migration.sql`; ის ამატებს owner/admin წაშლის RPC-ებსა და feed permission flag-ს ისე, რომ არსებული პოსტები და კომენტარები არ წაიშალოს. ძველი admin delete ფუნქციის წვდომას migration თავად აუქმებს.
3. **Project Settings → API**-დან დააკოპირე **Project URL** და **anon/public key**.
4. ჩასვი მნიშვნელობები `supabase-config.js`-ში:

```js
export const SUPABASE_URL = 'https://YOUR_PROJECT.supabase.co';
export const SUPABASE_ANON_KEY = 'YOUR_PUBLISHABLE_OR_ANON_KEY';
```

ბრაუზერში მხოლოდ anon/public key გამოიყენება. **არასოდეს ჩასვა `service_role` key, database password ან personal access token HTML/JS ფაილებში.** აპს ეს საიდუმლო გასაღებები არ სჭირდება.

5. **Authentication → URL Configuration**-ში დააყენე Site URL `http://localhost:4173` და Redirect URLs-ში დაამატე `http://localhost:4173/**`. გამოქვეყნების შემდეგ დაამატე შენი HTTPS დომენიც, მაგალითად `https://your-domain.example/**`.
6. **Authentication → Providers → Email**-ში ჩართე Email provider. Production-ზე ელფოსტის დადასტურება ჩართული დატოვე. რეალური წერილების გასაგზავნად **Authentication → SMTP Settings**-ში საკუთარი SMTP provider დააკონფიგურირე.

## ადმინისტრატორის ანგარიშის ჩართვა

1. აპის `auth.html` გვერდზე შექმენი პირადი ანგარიში და დაადასტურე ელფოსტა.
2. Supabase Dashboard-ის SQL Editor-ში გაუშვი ბრძანება და ელფოსტა ჩაანაცვლე შენით:

```sql
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"admin"}'::jsonb
where email = 'you@example.com';
```

3. აპიდან გამოდი და თავიდან შედი. ამის შემდეგ გამოჩნდება ადმინისტრატორის პანელი.

ადმინისტრატორის უფლება მოწმდება JWT-ის `app_metadata.role` მნიშვნელობითა და ბაზის `is_admin()` ფუნქციით. თითოეული ადმინისტრატორის RPC უფლებას სერვერზე ხელახლა ამოწმებს. მომხმარებელს საკუთარი თავის ადმინისტრატორად დაყენება ბრაუზერიდან არ შეუძლია.

## ლოკალურად გაშვება

FullLanguage რეჟიმის Windows PowerShell-ში, პროექტის საქაღალდიდან გაუშვი:

```powershell
.\serve.ps1
```

გახსენი <http://127.0.0.1:4173>. სერვერის გასაჩერებლად დააჭირე `Ctrl+C`. თუ PowerShell შეზღუდულ Constrained Language რეჟიმშია, გამოიყენე Python 3:

```powershell
python -m http.server 4173
```

ან VS Code-ის Live Server გაფართოება. `file://` მისამართი Auth redirect-ებისა და Realtime-ის შესამოწმებლად გამოსადეგი არ არის; გამოიყენე HTTP(S).

ამ სამუშაო გარემოში Python/Node არ არის დაყენებული, PowerShell კი შეზღუდულ რეჟიმშია, ამიტომ აქ HTTP server ვერ გავუშვი. HTML preview შემოწმებულია; რეალური backend-ის ტესტისთვის ჯერ Supabase პროექტი უნდა დააკონფიგურირო.

## ინტერნეტში გამოქვეყნება

ატვირთე ყველა ფაილი Netlify-ზე, Cloudflare Pages-ზე ან სხვა სტატიკურ ჰოსტინგზე; `index.html` განთავსების ძირეულ საქაღალდეში უნდა იყოს. `supabase-config.js`-ში მიუთითე Project URL და anon/public key. შემდეგ ჰოსტინგის HTTPS დომენი დაამატე Supabase Auth-ის Redirect URLs-ში. კლიენტის ეს მნიშვნელობები საჯაროა; ბაზაზე წვდომას RLS წესები იცავს.

## კონფიდენციალურობა და დაცვა

- საჯარო `public_feed` view ავტორის UUID-სა და ელფოსტას არ აბრუნებს. კომენტარის მონაცემებში მხოლოდ ID, ტექსტი და დროა; სხვა მომხმარებლები ავტორს „ანონიმი“-თ ხედავენ.
- ავტორის UUID და ელფოსტა მხოლოდ `admin_*` view-ებში, ადმინისტრატორის როლის მქონე პირს უჩანს. ადმინისტრატორს შეუძლია ანგარიშის დაკავშირება პოსტთან ან კომენტართან.
- `feed_events` არხი მხოლოდ ობიექტის ტიპს, ID-სა და მოქმედებას გადასცემს; ავტორის ID-ს, email-სა და კომენტარის ტექსტს არ გადასცემს.
- `post-images` Storage bucket საჯაროა: გამოქვეყნებულ ფოტოს ყველა ხედავს. ფაილის სახელი მომხმარებლის ID-ს არ შეიცავს; ატვირთვა და წაშლა RLS-ით იზღუდება. საჯარო ფოტოს URL-ის მქონე პირს მისი გაზიარება შეუძლია.
- Supabase Auth ამუშავებს პაროლს; პროფილში მხოლოდ შიდა UUID და დაბლოკვის სტატუსი ინახება. მონაცემთა ბაზა ზღუდავს წუთში 4 პოსტისა და 10 კომენტარის დამატებას და კრძალავს ერთი და იმავე კომენტარის ერთ პოსტზე ხუთ წუთში გამეორებას.
- ავტომატური შინაარსის მოდერაცია მიერთებული არ არის. გასაჩივრებას ადმინისტრატორი ხელით განიხილავს; Production-ზე მოაწესრიგე მოდერაციის, სარეზერვო ასლებისა და ინციდენტებზე რეაგირების პროცესი.
- ეს სერვისი სრულად ანონიმური არ არის: პროექტის მფლობელს/ადმინისტრატორს და Supabase/ჰოსტინგის მომწოდებლებს შეუძლიათ ანგარიშისა და შინაარსის დაკავშირება. IP/Auth ლოგებზეც მომწოდებლების პოლიტიკა ვრცელდება. ეს შეზღუდვა მომხმარებლებს `privacy.html`-ში ეცნობებათ.

## შეზღუდვა

Supabase პროექტი და credentials წინასწარ მოწოდებული არ არის. ამიტომ Auth, სხვა მოწყობილობებთან მონაცემების გაზიარება, Storage და Realtime რეალურ გარემოში მხოლოდ ზემოთ მოცემული ნაბიჯების შესრულების შემდეგ შემოწმდება. კონფიგურაციამდე აპი backend-ის მუშაობას არ აჩვენებს.
